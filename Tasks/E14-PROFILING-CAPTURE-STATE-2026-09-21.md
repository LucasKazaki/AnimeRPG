## Reproducible gap

The current capture-pair verifier proves that a profiled manifest contains frame/phase/process-memory evidence and that a control manifest omits those roles. It does **not** prove what the running process actually configured at startup. A control launch could accidentally inherit `ASTRAL_FRAME_TIMING_CSV`, `ASTRAL_FRAME_PHASE_TIMING_CSV`, or `ASTRAL_PROCESS_MEMORY_CSV`, collect data to an unlisted path, and still look like a capture-off control at manifest time. Conversely, a profiled manifest could list output files without a machine-verifiable startup record of the admitted warmup, limits, stride, and output identities.

This packet adds a fail-closed startup receipt generated by Astral after all three capture subsystems and benchmark run control are configured but before the frame loop begins. The receipt must describe only known profiling controls and must never dump unrelated process environment data.

Acceptance requires:

1. Benchmark mode requires `ASTRAL_PROFILING_CAPTURE_STATE_JSON` and rejects missing, malformed, invalid, unsafe, or overwriting receipt output before entering the frame loop.
2. The startup receipt records, for whole-frame timing, main-thread phase timing, and process-memory capture, whether the actual configured subsystem is `enabled` or `not_requested`.
3. Enabled streams bind their configured output path relative to the receipt directory plus warmup and sample limits. Process memory also binds sampling stride and the Windows process-counter source. Disabled streams record null settings rather than default-looking values.
4. The receipt binds the already-admitted benchmark fixed rate, warmup/measured frame counts, client area, windowed GDI presentation policy, input suppression, and exact-frame termination contract.
5. A Python verifier checks the receipt through the existing package/benchmark-manifest and run-control provenance chain. The profiled mode must prove all three captures enabled with sufficient admitted sample capacities and paths matching the manifest evidence; the control mode must prove all three were not requested and must omit all three capture-file roles.
6. The capture-pair verifier requires one valid startup receipt in both runs, with `profiled=enabled` and `control=disabled`, before it can emit a valid pair receipt.
7. `instrumentation_overhead_verified` stays false. Startup-state proof is necessary but not sufficient for an overhead result.

The receipt is written at startup, before the capture CSV files exist, so it cannot truthfully contain final CSV content hashes. Final evidence hashes remain the benchmark manifest's job after the run. The startup receipt instead binds configured output identities; the manifest later SHA-256-binds both the receipt and completed CSVs to the exact package.

## Current primary-source research, accessed 2026-09-21

Behavior references only. No proprietary source is copied and no external dependency is imported.

1. Epic Games, Unreal Engine 5.8, **Trace in Unreal Engine 5**:
   https://dev.epicgames.com/documentation/unreal-engine/trace-in-unreal-engine-5
   - Trace channels determine which event types are emitted and control trace data rate.
   - Applicability: capture enablement is a benchmark variable that must be explicit.
2. Epic Games, Unreal Engine 5.8, **Developer Guide to Tracing in Unreal Engine**:
   https://dev.epicgames.com/documentation/unreal-engine/developer-guide-to-tracing-in-unreal-engine
   - Channels constrain emitted events to reduce CPU and memory cost and are explicitly opted into.
   - Applicability: enabled/disabled instrumentation state can affect the measured workload.
3. Unity 6.0 (6000.0), **UnityEngine.Profiling.Profiler**:
   https://docs.unity3d.com/6000.0/ScriptReference/Profiling.Profiler.html
   - Unity states that using the Profiler negatively affects application performance and that a non-development build runs faster.
   - Applicability: Astral must prove capture state before interpreting profiled/control timing differences.
4. Microsoft, **Environment Variables (Win32)**:
   https://learn.microsoft.com/en-us/windows/win32/procthread/environment-variables
   - Every process has an environment block and a child inherits its parent's variables by default unless a different block is supplied at process creation.
   - Applicability: a control process can accidentally inherit profiling variables, so manifest role absence alone is not launch-state proof.
5. Microsoft, **Changing Environment Variables (Win32)**:
   https://learn.microsoft.com/en-us/windows/win32/procthread/changing-environment-variables
   - A child receives a copy of the inherited or explicitly supplied environment at process creation.
   - Applicability: record the running process's interpreted capture controls, not an operator's later reconstruction.

Licensing: public documentation is used only to define behavior and measurement requirements. This packet copies no Unreal Engine, Unity, or Microsoft implementation code and adds no third-party library.
